## Description
The description is the body text under '## Description', but `set` refuses the property and every --json payload exposes only `body` (description and notes together), so a machine caller must cut the body apart to read the description and rewrite the notes to change it. Storage does not change: the description stays in the body. See plans/milieu-cli-gaps.md.

Read: `show --json`, `list --json` and `search --json` gain a `description` key holding the text from the first '## Description' heading up to the next '## ' heading or the end of the body, null when the heading is absent. `body` stays as it is. One projection serves all three -- Ticket.to_dict (schema.py:304) -- so decide the blast radius deliberately: progress, delete, list --tree, deps --json and the claim payload print through it too (anchors in the plan doc). Narrower alternative: inject the key per command the way _cmd_list_raw injects `request` (cli.py:1735).

Write: `set <id> description <text>` replaces only that section and leaves the notes byte-for-byte. When the body has no '## Description' heading, insert the section at the top of the body and keep all the other text. Add a DESCRIPTION_HEADING constant plus extract/replace helpers in schema.py next to NOTES_HEADING (226), append_note (396) and notes_body (417) -- take the FIRST heading, since a description may quote one; notes_body deliberately uses the last. Add 'description' to SETTABLE_PROPERTIES (schema.py:504) but NOT to FIELD_ORDER: it is body text, like `body`. It is not a Ticket attribute, so it needs its own branch in cmd_set's application loop (cli.py:2938-2948, shaped like the `status` branch at 2941) instead of the generic setattr, and it must bypass coerce_field_value's comma-splitting and the CLEARABLE_TEXT_FIELDS clearing to None (schema.py:507/589).

Clear: an empty value empties the section and keeps the heading -- never None.

Reuse, do not duplicate: `create --description` and `promote --description` already write this section through schema.DEFAULT_BODY (108) and _promoted_body (cli.py:1402-1425), so keep one writer.

No sink code: both sinks store the body whole (file: canonical markdown via sinks/base.py:305; sqlite: tickets.body, sqlite.py:93) and `arbite migrate` copies bodies verbatim.

Docs: JSON_HELP (docs.py:66) and the conventions topic say --json field names match the frontmatter -- inaccurate once a derived key ships, so reword; document `description` in FIELD_NOTES (247)/_topic_fields (724); update the p_set help (cli.py:5108) and the cmd_set docstring (2898). `arbite docs commands set` renders from the parser.

Acceptance: set a description on a ticket that has notes -- the notes are unchanged and `show --json` reports the new text in `description`. Set a description on a ticket whose body has no heading -- the old text survives below the new section. `set <id> description ''` leaves '## Description' present and empty. A body with no heading yields description: null, not ''. Identical on the file and sqlite sinks.

Tests: tests/test_schema.py beside test_references_is_a_settable_property (79) for membership plus heading extract/replace; tests/test_cli.py extends test_show_json_exposes_the_frontmatter_contract (679, which asserts `body`) and test_set_validates_and_reports_what_it_changed (1436); a parity assertion in tests/test_sink_conformance.py beside test_body_survives_a_round_trip (48). No existing scenario in interaction-examples.md prints a body key, and LC5 pins only the status guard, so nothing there breaks; add an LC-family scenario for `set <id> description` if a transcript is wanted.
