## Description
Replace the file-based documentation surface (committed README.md, .arbite/AGENTS.md, .arbite/WORKSPACE.md and the AGENTS_EXAMPLE instructions block) with a command-line docs system: a token-light overview printed by 'arbite docs', and 'arbite docs <topic>' deep dives fetched on demand. Goal: one source of truth rendered from the installed version, so docs are never regenerated into git and cannot drift from the CLI/schema. Design proposal under discussion; structure to be approved before implementation.

PROPOSED: a single 'arbite docs' surface rendering from the installed version at runtime, nothing regenerated into git.

Command surface:
  arbite docs                    -> light overview (default; token-budgeted)
  arbite docs list               -> topic index (name + one-line summary, grouped)
  arbite docs <topic>            -> one deep dive
  arbite docs search <term>      -> topics/lines mentioning a term
  arbite docs commands [NAME]    -> per-command usage+flags, rendered from build_parser()
  arbite docs all                -> concatenation (export/regenerate a file if wanted)
  --json on any of the above for agents: {topic, summary, section, body}

Topic tree: workflow, fields, sinks, identity, triage, conventions, proxy, cmd, evidence, limits, config, commands, design, examples, upgrading. Default overview names only the ~8 commands a caller actually types and points at 'arbite docs list'.

Sink-awareness: topics inspect the active sink at runtime (same as init today: file vs sqlite prose + stale-store warning), so switching sinks never needs a doc regeneration.

Fate of files: .arbite/AGENTS.md becomes a tiny static pointer written once (run 'arbite docs'); .arbite/WORKSPACE.md deleted (its content is 'arbite docs proxy' + 'arbite docs commands'); README shrinks to install + landing + pointer, deep content moved to topics; instructions block updated to say 'run arbite docs'; INITIAL_DESIGN_DOC/plans left as history.

Tests: keep a budget test on the default overview, add coverage (every listed topic renders; every command reachable; only real vocabulary named), drop the AGENTS.md/WORKSPACE.md content tests.

Open forks to confirm with the user: (1) authoring model -- Python topic registry in docs.py vs bundled markdown files vs hybrid; (2) file fate -- thin pointer+delete WORKSPACE+slim README vs keep generating vs no files at all; (3) topic granularity.
