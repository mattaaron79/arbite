2. THE RC1 FLAKE -- reproduced with evidence, root cause found, message bug fixed, test corrected
Reproduction: 72 runs of the RC1 test at 6-way parallelism -> 7 failures (1 in 10), each
`assert [0, 1, 1, 4] == [0, 1, 1, 1]`. Forensics (a temporary harness that printed every worker's
stdout/stderr/code) gave the exact answer:
  busy: tic-cf9f already has an active attempt att-194f (claude.haiku.003, generation
  {holder.generation}); one active attempt per ticket, so it cannot be claimed again
Two findings:
  (a) A REAL BUG: the second line of `lifecycle._attempt_in_the_way`'s message was not part of the
      f-string, so the literal text `{holder.generation}` reached the user. Fixed (the line is an
      f-string now), and two tests now assert the generation is named and no `{holder` survives
      (`test_coordination_lifecycle.py::test_...` at the seeded attempt, and the RC1 loser branch).
  (b) The 4 itself is a DOCUMENTED outcome, not a defect: `claim` reads the ticket snapshot (CLI) and
      the live attempt (store) at different moments, and a winner writes the ticket then the attempt
      (two storage domains, one commit each). A loser whose snapshot still looked claimable when its
      attempt read lands sees a live attempt and gets outcome 4 `attempt_held` ("a live claim or
      attempt holds it; nothing changed" -- the exit-code vocabulary's own words, and the outcome
      `lifecycle._attempt_in_the_way` documents on purpose, with its own deterministic test).
      All three losing answers (CL3 lost-race exit 1, `attempt_held` exit 4, and the file sink's
      transient "no ticket found" during relocation) write nothing and name the holder, so the plan's
      RC1 target -- exactly one winner -- held in every observed run.
DECISION: the nondeterminism is in *which honest refusal* a loser sees, not in the outcome; both
codes are documented. So the fix is: (i) the message bug above, (ii) the RC1 test now accepts the
documented code sets `[0,1,1,1]` or `[0,1,1,4]` while still asserting the invariant in full (one
winner, losers silent on stdout, holder named, one active attempt, one attempt.started event, ticket
assigned to the winner, doctor clean). NO follow-up ticket was needed: nothing about the outcome is
nondeterministic, and the one real defect the flake exposed is fixed here.
Stress evidence after the fix: the same 72 runs at 6-way parallelism -> 72/72 pass.

HONEST LIMITS A USER SHOULD READ BEFORE ADOPTING THIS
- The proxy is not an enforcement layer: a shell, an editor or any other process can write bytes
  arbite never sees. Those bytes are drift, detected by the next read and attributed to no ticket, and
  arbite cannot prove who wrote a file (attribution only, never authentication).
- Observation is not exclusivity: `arbite cmd` observed mode claims nothing, and guarded mode checks
  before and after the run rather than during it, so a takeover mid-run is reported, not prevented.
  A killed guarded run leaves its claim for `doctor --fix` once the attempt is over.
- Reads are not isolated: a read can observe a commit in flight (the file sink reports
  `pending_commit`).
- Nothing runs in the background: no daemon, no agent launcher, no automatic stale recovery, no
  worktree workflow, no central database, no factory, no dashboard.
- Evidence is never pruned -- there is no retention policy yet, so the store grows with the work; one
  version is capped at 64 MiB and `arbite receipt --summary` is the export to take first.
- A claim racing a live attempt can be answered with exit 1 (CL3 lost-race) or exit 4
  (`attempt_held`), depending on which of the winner's two writes the loser's read sees. Both write
  nothing, name the holder and offer `list next --claim`; which one arrives is not deterministic (see
  the milestone note). No follow-up ticket was raised: the outcome is deterministic (exactly one
  winner) and both refusals are documented outcomes, and the message defect the reproduction exposed
  is fixed in this ticket.
- The frozen transcripts are reproduced by fixtures that build the line counts, paths and dates each
  block asserts; digests are normalised on both sides because they are facts about bytes that no
  fixture can rebuild. That is stated in the catalogue's own conventions now, along with the fact
  that the blocks were written against an earlier revision of this repository.
