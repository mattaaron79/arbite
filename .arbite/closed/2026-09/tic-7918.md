## Description
Planning key: C01
Handoff: .arbite/planning/shared-directory-coordination.md
Examples: .arbite/planning/interaction-examples.md (WS1, WS2, DR4)

## Outcome and scope
Introduce storage-neutral records for workspace, work attempt, file claim, read observation, operation receipt, artifact and event. Add schema revisions, opaque ids, UTC times, and a JSON result and error vocabulary that includes busies and stales. Establish an application layer for guarded multi-record operations so policy lives neither in argparse nor in SQL.

## Acceptance criteria
- Record fields and invariants match the coordination handoff; legacy tickets and timestamps stay readable.
- The workspace is derived from the located .arbite directory and the resolved sink; there is no bind command and no conflict path.
- Sink transaction, revision and recovery interfaces are defined for later slices; existing file and SQLite commands keep working.
- Identity attribution is documented as attribution, never as authentication.
- The examples harness exists: a helper that normalises ids, times and paths, with tests named after scenario ids.
- Scenarios WS1, WS2, DR4 pass exactly as written in the examples doc.

## Validation
Model serialisation and validation tests, old-store fixtures, existing schema and CLI regression tests, harness normalisation unit tests.

## Boundaries and handoff
Implement this slice only: no daemon, agent launcher, automatic stale recovery, worktree workflow, central database, factory or dashboard. Preserve both-sink behaviour. Sibling tickets may touch the same files; coordinate edits or work serially until the proxy exists. Record implementation decisions, validation results, observable behaviour and remaining limitations in ticket notes before close.

DECISIONS WORTH REVIEWING. (1) Coordination state lives with the STORE, not the project: file sink -> <sink root>/coordination (default .arbite/coordination), sqlite sink -> the ticket database; scratch stays project-anchored in .arbite/scratch per the handoff. (2) The workspace is derived from the located .arbite/ dir + resolved sink + sink root and is never bound: no bind command, no conflict path, and a relocated root/repointed store derives a different id. init is the one command that records the binding, and where the old record is superseded put_workspace deletes it (that is delete_record's only caller today). (3) arbite init now runs the coordination guards BEFORE creating anything (CoordinationApp.check_layout), creates the layout, and writes the workspace record last -- an interruption leaves an empty layout a re-run completes, never a record whose store is missing. (4) JSON carries plain paths while the text lines print a trailing slash for a directory root: the DR4 transcript prints its roots without one, and a machine consumer must not strip punctuation. (5) Read observations and receipts share the op- id space, because the id IS the token a write presents; authorizes_write() requires an active claim held by the same attempt at the observed generation and never accepts an absent-path probe, while authorizes_creation() accepts exactly the absent probe. (6) doctor --json gained 'coordination' (kind, root, claims_active, events, pending_operations) and 'scratch' (files, bytes); doctor's TEXT output is deliberately unchanged (the note lines and their guidance are tic-95c0/DR3's, and the coordination findings become problems with tic-b03b).
