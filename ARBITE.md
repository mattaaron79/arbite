## What this is

`arbite` is a low-tech, file-based ticketing system that lives inside this git repo. Tickets are markdown files with YAML frontmatter, stored under `tickets/`, moved between folders as their status changes -- no database, no server. It exists so multiple AI agents (and humans) can pick up tasks, track state, and leave a clean git history of what happened and when.

**Any agent or human working in this repo should use `arbite` for creating, claiming, blocking, and closing tasks instead of ad hoc notes or files.** The ticket's folder location is the single source of truth for its state -- an agent's own memory of what it was doing is only a hint, and must be checked against the ticket's actual location before being trusted. Agents should also prefer `arbite note` over directly editing a ticket file to leave progress notes -- it timestamps and attributes the entry consistently instead of relying on freeform hand edits.

## Directory layout

```
tickets/
  open/            actionable, unclaimed
  in_progress/     claimed, being worked
  blocked/         stalled, see blocked_by
  closed/YYYY-MM/  archived by close date
  agents/          one scratchpad file per agent identity
```

Status is represented by folder location, not just a frontmatter field -- `status` mirrors the folder and is kept in sync by every state-changing command in the same operation. Filenames stay stable across moves, so `git log --follow` on a ticket file traces its full lifecycle as folder-move commits.

## Ticket frontmatter fields

- `id` -- unique ticket id, e.g. tic-a1b2 -- generated by `arbite create`, never set by hand
- `title` -- short human-readable summary
- `status` -- open | in_progress | blocked | closed -- mirrors the ticket's folder, kept in sync by every arbite command
- `type` -- bug | feature | refactor | chore
- `tier` -- low | medium | high | frontier -- agent capability level required to work the ticket
- `domain` -- what kind of agent/tool this needs, e.g. mesh, image_gen, audio_gen, ui, io -- drives routing
- `priority` -- numeric urgency index, lower = more urgent (e.g. 1 is highest priority) -- used to order which workable ticket to pick up next; unset (null) sorts last
- `tags` -- freeform list, for human/codebase-area search -- distinct from domain
- `assignee` -- agent id currently working the ticket, e.g. claude.haiku.001, or null if unclaimed
- `depends_on` -- list of other ticket ids that must close first (structural)
- `blocked_by` -- freeform reason OR a ticket id -- why it's stalled, only meaningful when status: blocked
- `created` -- date created (YYYY-MM-DD)
- `updated` -- date of the most recent status change
- `closed` -- date closed (YYYY-MM-DD), null until closed -- drives which closed/YYYY-MM/ folder it archives into

`depends_on` (structural, ticket ids) and `blocked_by` (freeform, human-readable) are deliberately separate fields -- don't collapse them. `tier` (capability level) and `domain` (specialization) are independent axes. `domain` (routing) and `tags` (search) serve different purposes even though both are strings. `priority` (urgency) is independent of `tier` (capability): a trivial chore can still be urgent. When choosing between workable tickets, pick the one with the lowest `priority` number first.

## Agent identity and resuming work

Agent ids follow `company.model.instance`, e.g. `claude.haiku.001`. Each agent has a scratchpad at `tickets/agents/<agent_id>.md` for recording what it's currently working on. To resume across sessions: check your own scratchpad for a last-known ticket id, then verify that ticket is still in `tickets/in_progress/` with `assignee` matching your own id -- the ticket's folder is ground truth, the scratchpad is only a hint. If the scratchpad is absent, stale, or mismatched, fall back to scanning `tickets/in_progress/` for a ticket assigned to you.

## Typical workflow

```
arbite list --status open --domain mesh --tier medium   # find something to work
arbite list next --tier high                            # grab the next workable open ticket
arbite show tic-a1b2                                    # read it in full
arbite claim tic-a1b2 --agent claude.haiku.001          # take it
arbite note tic-a1b2 claude.haiku.001 "progress update" # ...do the work, log progress...
arbite block tic-a1b2 --reason "waiting on tic-c3d4"    # if stalled
arbite close tic-a1b2                                   # when done
```

A human can also scaffold a ticket to fill in by hand later with `arbite create --blank` (optionally combined with any of --title/--type/--tier/--domain for whatever's already known). It fills in only the structural fields and leaves the rest as TODO placeholders, with a body warning telling agents not to claim it until it's been completed and saved.

### `arbite list`

```
usage: arbite list [-h] [--status {open,in_progress,blocked,closed}]
                   [--tier {low,medium,high}] [--domain DOMAIN]
                   [--priority PRIORITY] [--assignee ASSIGNEE]
                   [--tic TICKET_ID] [--tree | --topo]
                   [SUBCOMMAND]

List tickets, optionally filtered by one or more fields. Sorted so that within
a status, more urgent tickets (lower priority number) come first.

positional arguments:
  SUBCOMMAND            'next' prints a single list entry for the next open
                        ticket in topological dependency order (most urgent
                        first); combine with --tier to restrict to a
                        capability tier

options:
  -h, --help            show this help message and exit
  --status {open,in_progress,blocked,closed}
                        filter by status
  --tier {low,medium,high}
                        filter by tier
  --domain DOMAIN       filter by domain
  --priority PRIORITY   filter by exact priority number (lower = more urgent)
  --assignee ASSIGNEE   filter by assignee agent id
  --tic TICKET_ID       filter by comma-separated ticket ids, each a wildcard
                        (substring) match, e.g. 'f6' finds tic-f607; combine
                        with --tree/--topo to root the dependency view at the
                        matching tickets and pull in every transitive
                        dependency beneath them
  --tree                render the list as a dependency tree (children =
                        depends_on) instead of a flat table; siblings sorted
                        by priority
  --topo                render the list as a vertical list in topological
                        dependency order; when several tickets are ready at
                        once, the most urgent (lowest priority number) comes
                        first
```
